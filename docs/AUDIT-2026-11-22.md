# Аудит CurseTorrent от интерфейса до ядра

Дата проверки: 22 ноября 2026 года. Проверяемая версия: 0.1.0 preview, исходный коммит [`b2aa337a17ebb5351d122de1927eebb5ba484116`](https://github.com/jumonja-maker/CurseTorrent/commit/b2aa337a17ebb5351d122de1927eebb5ba484116), соответствующий выпуску [`v0.1.0-preview.4.1`](https://github.com/jumonja-maker/CurseTorrent/releases/tag/v0.1.0-preview.4.1). Движок: MonoTorrent 3.0.2. Интерфейс: WPF, .NET 10, Windows x64.

## Заключение

CurseTorrent выполняет основные операции настоящего торрент-клиента: скачивает и раздает файлы, получает метаданные magnet, сохраняет задачи, работает с выбранными файлами. Это подтверждено передачей контрольных данных и проверкой их содержимого. Однако текущая версия требует исправлений до стабильного выпуска. Главный недостаток — сохранность уже существующих файлов: перепроверка может усечь файл, а явно пропущенный нулевой файл раздачи способен обнулить другой файл с тем же именем. Также обнаружены неверное восстановление готовности файлов, ошибки быстрых переходов между состояниями и недостатки восстановления сеанса.

Практическая рекомендация для этой preview: использовать отдельную папку с тестовыми данными, пока не исправлены случаи изменения существующих файлов. Успешная сборка и штатная загрузка не дают основания считать эти сценарии безопасными. Аудит не изменяет программу: в отдельную ветку добавлены диагностические проверки, свидетельства и этот отчет. `main`, пользовательские загрузки и опубликованный пакет не менялись.

## Объем и метод

Проверены все продуктовые C# и XAML компоненты, PowerShell-установщик и удаление, сценарий сборки и выпуска, lock-файлы зависимостей, пользовательская документация. Отдельно прочитаны относящиеся к находкам участки точной зависимости MonoTorrent 3.0.2, commit [`e78faebd0aec117146cffccaaea987ab0629eec0`](https://github.com/alanmcgovern/monotorrent/tree/e78faebd0aec117146cffccaaea987ab0629eec0). Это необходимо: часть файловых операций и переходов состояния выполняется внутри движка, вне адаптера CurseTorrent.

Использовались три вида проверки: чтение кода с прослеживанием вызовов, выполнение настоящего Core на временных файлах, выполнение нативных WPF-окон на Windows. Сетевые передачи проводились между локальными участниками BitTorrent и собственным UDP-трекером. В UI-стенде использованы реальные классы окон и исходные ресурсы оформления, а данные списка задач заменены контрольными снимками. Это позволяет проверить привязки, сортировку и геометрию без обращения к пользовательскому профилю.

Основные свидетельства:

- [Первый Windows-аудит](https://github.com/jumonja-maker/CurseTorrent/actions/runs/44997373944/job/137131216818): исходные 44 проверки, шесть сетевых сценариев, файловые дефекты, восстановление состояния, ошибка быстрого переключения, установщик.
- [Второй Windows-аудит](https://github.com/jumonja-maker/CurseTorrent/actions/runs/44997616362): повтор основных сценариев, измерение отмены и первый успешный запуск диагностического UI-стенда.
- [Итоговый UI-аудит Windows](https://github.com/jumonja-maker/CurseTorrent/actions/runs/44998349506): проверка отображаемого текста приоритетов, размеров столбцов и исправленный захват окон. Изменения диагностического стенда не меняли приложение.
- [CI исходного опубликованного коммита](https://github.com/jumonja-maker/CurseTorrent/actions/runs/44995785869): сборка пакета, запуск упакованного exe, базовая отрисовка и установка.
- Исходники диагностических проверок находятся в `audit/`, журналы — в `audit/evidence/`. Диагностическая проверка может успешно завершиться, зафиксировав неправильное поведение. Зеленый шаг такого стенда не означает отсутствие дефектов.

Приоритеты: **P1** — исправить до использования с ценными данными; **P2** — исправить до стабильной версии, поскольку нарушается корректность, доступность или восстановление; **P3** — ограниченный интерфейсный или проверочный недостаток. Это рабочая очередность, а не оценка CVSS. Подтвержденные результаты выполнения отделены от выводов только по коду.

## Подтвержденные дефекты

### F01 Перепроверка усекла уже существующий файл

**P1. Воспроизведено на Linux и Windows.** В выбранной папке находился контрольный `notes.txt` размером 131 072 байта. Добавлена на паузе раздача, в которой одноименный файл должен занимать 32 768 байт. Добавление сохранило файл. После команды перепроверки остался `notes.txt.!mt` размером 32 768 байт. Исходное имя исчезло, SHA-256 изменился, потеряно 98 304 байта. Передачи по сети не было, приложение не сообщило об ошибке.

Это требует совпадения имени в выбранной папке. Произвольные файлы за ее пределами тест не затрагивал. Сценарий реалистичен при повторном использовании папки или проверке найденных данных: пользователь просит проверить содержимое, а проверка его изменяет.

В `ValidateAndReservePaths` путь проверяется на допустимость и конфликт с другими зарегистрированными задачами. Существующий посторонний файл отдельного статуса не получает. `GuardedPieceWriter.ReadAsync` затем передает чтение `DiskWriter`, который перед первым открытием может вызвать `MaybeTruncate` и уменьшить длину файла. Защита принадлежности пути не обеспечивает чтение без изменения данных.

**Исправление:** отдельная политика конфликтов с существующими файлами, безопасное чтение при проверке, отсутствие усечения и переименования чужого файла без явного решения пользователя. Проверять и конечное имя, и `.!mt`. **Приемка:** добавление на паузе, отмена добавления и перепроверка не меняют имя, размер и SHA-256 существующего контрольного файла; разрешенная замена имеет отдельный понятный сценарий.

Источники: [резервирование путей](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/TorrentService.cs#L654-L681), [защищенное чтение](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/GuardedPieceWriter.cs#L35-L38), [DiskWriter](https://github.com/alanmcgovern/monotorrent/blob/e78faebd0aec117146cffccaaea987ab0629eec0/src/MonoTorrent.PieceWriter/MonoTorrent.PieceWriter/DiskWriter.cs#L245-L252), [фактическое усечение](https://github.com/alanmcgovern/monotorrent/blob/e78faebd0aec117146cffccaaea987ab0629eec0/src/MonoTorrent.PieceWriter/MonoTorrent.PieceWriter/RandomFileStream.cs#L25-L30). Проверка: `audit/security/repro`, режим `existing`.

### F02 Пропущенный нулевой файл обнулил существующий

**P1. Воспроизведено на Linux и Windows.** Многофайловая раздача содержит обычный файл и `notes.txt` длиной 0. По этому пути уже находится контрольный файл размером 131 072 байта. Для него выбран `Skip`, что подтверждается снимком Core. После продолжения раздачи с другим выбранным файлом `notes.txt` становится пустым: 131 072 → 0 байт. Пиров нет, ошибка отсутствует, статус задачи — Downloading.

Причина — `StartingMode.CreateEmptyFiles` в MonoTorrent создает все нулевые файлы независимо от приоритета и вызывает `SetLength(0)` напрямую. Этот вызов обходит `IPieceWriter`. В CurseTorrent уже предусмотрен отдельный этап получения magnet-метаданных для ограничения такого обхода, но он не защищает посторонние существующие файлы и не обеспечивает смысл команды «Не скачивать».

**Исправление:** создание нулевых файлов должно учитывать Skip и общую политику сохранности существующих данных. Нужен контролируемый путь в движке или проверенная замена затронутой реализации; расширения одного `GuardedPieceWriter` недостаточно. До исправления запуск при таком конфликте следует отклонять. **Приемка:** Skip не создает отсутствующий нулевой файл и не изменяет уже существующий, в том числе после паузы и перезапуска.

Источники: [применение приоритета](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/TorrentService.cs#L258-L268), [известный обход writer](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/TorrentService.cs#L218-L224), [создание нулевых файлов движком](https://github.com/alanmcgovern/monotorrent/blob/e78faebd0aec117146cffccaaea987ab0629eec0/src/MonoTorrent.Client/MonoTorrent.Client.Modes/StartingMode.cs#L156-L169). Проверка: режим `skipzero`.

### F03 Измененный файл отображается как полностью готовый

**P2. Воспроизведено на Linux и Windows.** Корректный файл размером 131 072 байта полностью проверен, приложение штатно закрыто. Затем тест заменил его одним байтом. После запуска CurseTorrent восстановил `Progress=100` и `DownloadedBytes=131072`; после Resume состояние стало `Seeding`, хотя физический размер был 1 байт. Ручная перепроверка вернула прогресс к 0%.

Само усечение в этом сценарии выполняет тест, моделируя внешнее изменение. Ошибка приложения — доверие устаревшему кэшу и неверное сообщение о готовности. Подтвержденная смена размера не замечается даже без вычисления новых хешей.

CurseTorrent включает fast resume в режиме `Accurate`, а движок загружает сохраненные битовые поля и выставляет `HashChecked=true`. При старте проверяется наличие файлов, но не совпадение размеров и меток изменения. Название режима `Accurate` не заменяет проверки конкретного поведения зависимости.

**Исправление:** хранить признаки файлов, на которых основан кэш, и сбрасывать его при несовпадении. Минимум — размер и время изменения; для строгой проверки содержимого нужен hash check. **Приемка:** удаление, усечение, изменение размера и замена файла при закрытом приложении не приводят к достоверным 100% без необходимой проверки. Полная перепроверка при каждом запуске надежна, но медленнее для больших коллекций; контроль признаков позволяет выбирать более практичную политику.

Источники: [настройки fast resume](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/TorrentService.cs#L598-L604), [восстановление битовых полей](https://github.com/alanmcgovern/monotorrent/blob/e78faebd0aec117146cffccaaea987ab0629eec0/src/MonoTorrent.Client/MonoTorrent.Client/Managers/TorrentManager.cs#L1063-L1080), [проверка только существования](https://github.com/alanmcgovern/monotorrent/blob/e78faebd0aec117146cffccaaea987ab0629eec0/src/MonoTorrent.Client/MonoTorrent.Client.Modes/StartingMode.cs#L203-L216). Проверка: режим `changed-payload`.

### F04 Пауза magnet задерживает все управляющие команды

**P2. Воспроизведено на Linux и Windows.** Добавлена magnet-ссылка с локальным UDP-трекером, который принимает запросы и не отвечает. Пока метаданные не получены, вызвана Pause, затем изменение настроек. Через 3 секунды обе операции еще ожидали. Пауза завершилась через **60,035 секунды в Linux и 60,036 секунды в Windows**, после чего применились настройки.

Заблокирован общий семафор команд Core. Это не означает зависание отрисовки WPF: измерялась доступность команд. В UI на время операции отключается панель управления. Удаление и завершение используют тот же helper остановки, поэтому также зависят от длительности сетевой очистки, хотя полное время выхода окна отдельно не измерялось.

Обычный torrent останавливается с явным двухсекундным ограничением announce. Metadata-only magnet отменяет токен и ожидает весь `DownloadMetadataAsync`; внутри MonoTorrent вызывается `StopAsync()` без этого ограничения. Общий внутренний предел остановки — одна минута.

**Исправление:** управляемая metadata-операция с ограниченным временем остановки и короткая область удержания общего семафора. Простое прекращение ожидания по таймауту не завершает скрытый менеджер и может создать новый конфликт при Resume. **Приемка:** pause/remove/exit имеют небольшой документированный предел ожидания, другие задачи доступны, повторный Resume не создает дубликат менеджера.

Источники: [PauseAsync](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/TorrentService.cs#L374-L384), [StopEntryAsync](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/TorrentService.cs#L518-L538), [получение метаданных](https://github.com/alanmcgovern/monotorrent/blob/e78faebd0aec117146cffccaaea987ab0629eec0/src/MonoTorrent.Client/MonoTorrent.Client/ClientEngine.cs#L582-L598), [внутреннее ожидание](https://github.com/alanmcgovern/monotorrent/blob/e78faebd0aec117146cffccaaea987ab0629eec0/src/MonoTorrent.Client/MonoTorrent.Client.Modes/StoppingMode.cs#L100-L109). Проверка: `metadata-stop`.

### F05 Быстрое управление вызывает ошибку остановки

**P2. Воспроизведено на Windows, зависит от расписания потоков.** В последовательности Recheck, затем поставленных в очередь Resume и Pause первая Windows-итерация завершилась `ObjectDisposedException`: движок прочитал токен уже освобожденного `CancellationTokenSource`. Публичные команды при этом сериализуются семафором CurseTorrent. Первый Linux-прогон прошел, повторный обнаружил нарушение ожидаемого итогового состояния; это нестабильная гонка, а не гарантированное падение при каждом нажатии.

Во втором Windows-прогоне все 31 проверки этой серии прошли. Это подтверждает зависимость воспроизведения от расписания выполнения и не отменяет исключение первого Windows-прогона.

Стек Windows: `StoppingMode.Token` → `TorrentManager.StopAsync` → `TorrentService.StopEntryAsync:533` → `PauseAsync:381`. Тест проверяет реальные операции Core. Окно сообщения WPF с этой конкретной ошибкой не снималось; финальное сетевое состояние в первом сбое не фиксировалось.

Установленный факт — запрос паузы завершился исключением. По коду движка наиболее вероятен поздний переход незавершенного `StartingMode`, который после асинхронного ожидания меняет режим и освобождает уже установленный `StoppingMode`. Это объяснение подтверждается структурой кода, но полная трассировка всех внутренних переходов не выполнялась.

**Исправление:** согласовать весь жизненный цикл внутренних start/stop-переходов и отмену в адаптере или движке. Простое подавление исключения способно скрыть неверное состояние. **Приемка:** быстрые start/pause, recheck/pause/resume, remove и exit проходят на Windows; подтвержденная пауза означает реальное прекращение передачи, а поздние продолжения не возвращают задачу в работу.

Источники: [остановка в CurseTorrent](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/TorrentService.cs#L518-L538), [остановка в движке](https://github.com/alanmcgovern/monotorrent/blob/e78faebd0aec117146cffccaaea987ab0629eec0/src/MonoTorrent.Client/MonoTorrent.Client/Managers/TorrentManager.cs#L785-L804), [поздние переходы StartingMode](https://github.com/alanmcgovern/monotorrent/blob/e78faebd0aec117146cffccaaea987ab0629eec0/src/MonoTorrent.Client/MonoTorrent.Client.Modes/StartingMode.cs#L130-L153). Проверка: `transitions`, первый Windows-журнал.

### F06 Семантически поврежденная сессия обходит резервное восстановление

**P2. Воспроизведено на Linux и Windows.** Основной `session.json` заменен на `{}`, а `.bak` содержит исправную сессию с одной задачей. Приложение запускается с нулем задач без предупреждения. При закрытии основная сессия записывается пустой, а исправная резервная копия заменяется прежним `{}`. Загрузки на диске сохраняются, но рабочий список задач утрачен.

При `Torrents:null` запуск, наоборот, блокируется, хотя корректная копия существует. Некорректная строка приоритета, вызывающая `JsonException`, восстанавливается правильно. Значит, защита работает для синтаксических ошибок и ошибок типов, но не охватывает всю структуру и обязательные значения документа.

Тест намеренно создал семантически неправильный JSON. Не установлено, что штатная атомарная запись сама генерирует `{}` при аварии. Это дефект восстановления поврежденного или измененного файла, а не доказательство самопроизвольного исчезновения задач.

**Исправление:** валидировать обязательные поля и значения до принятия сессии и включить эту валидацию в восстановление. Сохранять последнюю пригодную копию. Неизвестную будущую версию формата продолжать отклонять без перезаписи, чтобы не повредить данные после отката приложения. **Приемка:** пустой объект, отсутствующий или null-список, некорректные записи и отрицательные счетчики обрабатываются явно и не затирают пригодную сессию.

Источники: [значения модели по умолчанию](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/TorrentService.cs#L15-L29), [загрузка сессии](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/TorrentService.cs#L87-L104), [атомарное хранение и fallback](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/AtomicJsonFile.cs#L14-L62). ### F07 Некорректные метаданные завершили процесс

**P2. Наблюдалось на Linux при вызове `InspectAsync` настоящего Core в отдельном диагностическом процессе; готовый Windows exe этим входом не проверялся.** При осмотре небольшого некорректного `.torrent`, не превышающего лимит 16 МиБ, диагностический процесс завершился с `Stack overflow`, exit 134. Обычный обработчик исключений не был достигнут. Сохранено описательное свидетельство; специальный вход и его генератор не включены в материалы аудита.

Проверка размера выполняется до рекурсивного разбора bencode, а `ValidateMetadata` — после него. В проверенном декодере нет достаточного ограничения вложенности. Ограничение байтов не ограничивает глубину структуры. Это отказ в доступности при открытии некорректного входа; выполнение произвольного кода или сетевой вариант атаки не установлены.

**Исправление:** ограничить глубину, число объектов, длины и общий ресурсный бюджет до рекурсивного декодера либо использовать декодер с такими пределами. Обычный catch не заменяет предотвращение переполнения стека. **Приемка:** набор безопасных граничных входов отклоняется понятной ошибкой, остальные загрузки и процесс продолжают работу.

Источники: [предел размера](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/TorrentInput.cs#L28-L33), [порядок разбора](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/TorrentService.cs#L124-L135), [рекурсивный декодер](https://github.com/alanmcgovern/monotorrent/blob/e78faebd0aec117146cffccaaea987ab0629eec0/src/MonoTorrent.BEncoding/MonoTorrent.BEncoding/BEncodeDecoder.Stream.cs#L109-L146).

### F08 Прерванная первая установка блокирует повторную попытку

**P2. Воспроизведено в Windows PowerShell 5.1.** В тестовом пакете один обычный файл был занят эксклюзивной файловой блокировкой. Прерванную первую установку нужно распознавать и продолжать либо очищать только свои файлы. **Приемка:** ошибка копирования не портит действующую версию, повторная попытка выполняется, посторонние файлы сохраняются.

Источники: [проверка непустой папки](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/scripts/install.ps1#L28-L39), [копирование](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/scripts/install.ps1#L41-L50), [запись manifest](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/scripts/install.ps1#L104-L111). ### F12 Начальные окна выходят за рабочую область

### F13 Минимальная ширина обрезает значения столбцов

## Интерфейс, доступность и производительность

Визуальная основа последовательна: единая темная палитра, читаемая иерархия заголовков, компактная панель действий и отдельная область файлов. Диалог добавления обычного `.torrent` помещает имя, папку, выбор файлов и подтверждение в одном окне. Формулировка удаления объясняет, что файлы сохраняются. Главная потребность сейчас — исправить конкретные состояния F09–F13, а затем расширять функции.

## Риски и ограничения по результатам чтения кода

### Ограничение magnet применяется слишком поздно

**P2, кодовый путь подтвержден, исчерпание памяти не воспроизводилось.** Лимит 16 МиБ в `ObserveMetadataDownloadAsync` проверяется после возврата из `DownloadMetadataAsync`. Ранее MonoTorrent резервирует буфер по `metadata_size`, объявленному пиром, без видимого верхнего предела в проверенном пути. Нужен лимит до выделения памяти и ограничение числа одновременно получаемых метаданных. Это отдельное свойство от размера готового `.torrent`; проверка результата после выделения не защищает саму стадию получения.

Источники: [поздняя проверка приложения](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/TorrentService.cs#L277-L286), [выделение буфера движком](https://github.com/alanmcgovern/monotorrent/blob/e78faebd0aec117146cffccaaea987ab0629eec0/src/MonoTorrent.Client/MonoTorrent.Client.Modes/MetadataMode.cs#L312-L322), [декодирование размера](https://github.com/alanmcgovern/monotorrent/blob/e78faebd0aec117146cffccaaea987ab0629eec0/src/MonoTorrent.Messages/MonoTorrent.Messages.Peer.Libtorrent/ExtendedHandshakeMessage.cs#L103-L106).

### Проверка файловых имен и ссылок имеет границы

**P3 для неполных правил имен.** Проверка COM/LPT охватывает ASCII-цифры, но пропускает зарезервированные Windows варианты с надстрочными ¹, ² и ³. Пригодность всей длины пути и сегментов для целевого тома также не проверяется заранее. Ожидаемый эффект — поздняя файловая ошибка; более серьезный эффект не установлен. См. [код проверки](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/TorrentInput.cs#L48-L60) и [официальные правила Windows](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file).

Проверка reparse points охватывает уже существующие вложенные пути в момент резервирования. Алиасы корня, hard links и замена каталога другим локальным процессом после проверки не закрыты этой моделью. Эти условия требуют дополнительного локального контроля; аудит не называет их доказанным удаленным выходом из папки. Политику ссылок и допустимого назначения стоит сформулировать явно и проверять тем способом, который обеспечивает реальные границы Windows-файловой системы.

## Архитектура и сопровождение

Разделение на WPF и `ITorrentService` удачно: интерфейс можно проверять с контрольными снимками, а настоящее ядро — без графической среды. Immutable snapshots уменьшают связь между потоками движка и элементами окна. Отдельное хранение своих копий `.torrent` позволяет продолжать работу после удаления исходного файла. Атомарная запись JSON, backup и откат при ошибках уже дают полезную основу. [Контракт ядра](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/Models.cs#L18-L44), [атомарная запись](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/AtomicJsonFile.cs#L48-L62).

Основная техническая проблема — предположения об API движка. Чтение может изменять файл; операция Start может завершиться раньше внутренних переходов; отмена metadata не означает быструю остановку; fast resume не обнаруживает каждое изменение данных. Исправления должны опираться на тесты этих свойств, а не только на названия методов. Полная перепись интерфейса или замена стека не требуется для устранения найденного, но граница адаптера нуждается в более строгом контракте.

После исправления функциональных проблем полезно разделить `TorrentService` на небольшие части: хранение и восстановление, жизненный цикл задачи, политика файлов и адаптер MonoTorrent. Это рекомендация по сопровождению, не самостоятельный дефект. Список `_backgroundTasks` сейчас удерживает завершенные операции без удаления; значительное потребление памяти не измерено, но для долгоживущего процесса лучше хранить только активные задачи. `GetSnapshots` повторно обходит файлы всех торрентов, поэтому стоимость обновления зависит от суммарного числа файлов, даже если таблица виртуализирована. [Фоновые операции](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/TorrentService.cs#L387-L423), [снимки](https://github.com/jumonja-maker/CurseTorrent/blob/b2aa337a17ebb5351d122de1927eebb5ba484116/src/CurseTorrent.Core/TorrentService.cs#L324-L351).

## Очередность исправлений

1. **Сохранность файлов:** F01 и F02; единая политика существующих данных и безопасная перепроверка. Эти ошибки непосредственно изменяют файлы пользователя.
2. **Достоверность и управление:** F03–F06; инвалидация устаревшего resume, надежные start/stop, ограниченная отмена metadata, сохранение пригодной резервной сессии.
3. **Некорректные входы и установка:** F07–F08 и лимит памяти до получения metadata; понятная ошибка без завершения процесса, безопасный повтор установки.
4. **Интерфейс:** читаемый приоритет, доступные кнопки при длинном имени и малой рабочей области, числовая сортировка и ширины столбцов; затем проверка горизонтальной прокрутки, клавиатурного фокуса и высококонтрастной темы.
5. **Закрепление результата:** включить воспроизводящие сценарии в постоянный Windows CI, проверить упакованный exe, затем выполнить короткую ручную проверку на Windows 11 и реальной сети.

Дополнительные функции — очередь загрузок, ограничения раздачи, подробные трекеры/пиры, изменение папки готовой задачи, выбор файлов magnet до начала payload, контекстное меню и массовые команды — следует планировать отдельно. Их отсутствие не выдается за найденную уязвимость. Для классического клиента наиболее полезен выбор файлов magnet после получения метаданных и до начала загрузки: сейчас все файлы начинают скачиваться по умолчанию, что прямо описано в интерфейсе и README.

## Границы заключения

Аудит охватывает текущий код, дополнительные сценарии выполнения и отрисовку реальных окон. Он не гарантирует отсутствие всех возможных дефектов. Не проводились длительный внешний swarm-тест, работа через конкретный роутер/VPN, полноценная IPv6-проверка, исчерпание диска, отключение питания, sleep/resume и съемный диск, тест SmartScreen/подписи издателя, полный цикл ассоциаций и трея на пользовательском ноутбуке, проверка screen reader и всех DPI-режимов.

Сборки Windows в GitHub Actions подтверждают поведение в среде runner, но не заменяют тест на конкретном Windows 11 компьютере. Ресурсный риск metadata и часть замечаний доступности получены из кода; они отдельно обозначены. Аварийное завершение парсера наблюдалось только в Linux. Причина гонки start/stop в деталях является выводом из кода; сам сбой подтвержден журналом Windows. Пользовательские файлы для тестов не использовались.

**Решение по выпуску:** сохранить статус preview. Переход к стабильной версии обоснован после устранения двух ошибок изменения файлов, восстановления достоверного состояния и прохождения постоянных регрессионных проверок на Windows.
